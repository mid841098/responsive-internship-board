Full Stack Development

Internship Board Product Brief

Scenario: Build a student internship board for a fictional organisation. Users must be able to search, filter by domain and work mode, inspect details, and submit an application.

Required records

Use the supplied JSON seed. Preserve each record ID, but you may extend the schema. Your API must return a predictable envelope containing status, data, and pagination metadata.

Acceptance criteria

  • Keyboard users can operate search, filters, cards, dialogs, and forms.
  • The list has loading, empty, error, and retry states.
  • The server rejects missing names, invalid email addresses, unsafe URLs, and duplicate applications.
  • Logs never contain passwords, access tokens, or full applicant records.
  • The final app works at 360px without horizontal scrolling.

Submission checklist

Include setup, environment-variable examples without secrets, schema and seed commands, test results, accessibility evidence, deployed URL, and a two-minute walkthrough.

Data handling

Pharmacovigilance

Fictional Safety Case and Expectedness Reference

Training only: all products, people, cases, and events below are fictional. This pack is not medical advice and must not be used for real safety reporting.

Fictional reference product: Velunex

For this exercise only, the supplied fictional reference lists these expected adverse reactions: transient headache, nausea, dizziness, and less commonly a mild self-limiting rash. No other event is listed as expected. “Expected” here means consistent with this supplied training reference; it does not mean common, harmless, or caused by the product.

Assessment rules

ConceptTraining rule
SeriousnessClassify using outcome criteria such as death, life threat, hospitalisation, disability, congenital anomaly, or another medically important condition.
SeverityIntensity (for example mild/moderate/severe). A severe symptom is not automatically a serious case.
ExpectednessCompare the reported event term and nature with the fictional Velunex list above.
CausalityRecord a reasoned likelihood category; never state that the exercise proves causation.

Task 3 supplied cases

  1. PV-201: dizziness began two hours after first use, resolved the same day, no treatment or hospitalisation.
  2. PV-202: appendicitis occurred three weeks after first use and required hospitalisation; medical history is incomplete.
  3. PV-203: mild rash began on day four, improved after stopping, no rechallenge.
  4. PV-204: loss of consciousness with emergency admission on day two; concomitant products and test results are unknown.

For each case, state: valid-case elements, seriousness and criterion, severity if supplied, expectedness against this Velunex reference, cautious causality reasoning, missing information, and follow-up questions.

Official learning references

  • ICH E2A: Clinical Safety Data Management
  • WHO–UMC causality assessment system
  • FDA: What is a Serious Adverse Event?

Ethical Hacking

Authorised Isolated-Lab Rules of Engagement

Hard boundary: work only on systems you own or an intentionally vulnerable local lab you are explicitly authorised to test. Never target EdVyro, another student, a public IP, or a third-party account.

Allowed scope

  • Localhost, a private host-only VM network, OWASP Juice Shop, or DVWA that you installed yourself.
  • Manual inspection and low-rate tools configured for the isolated target.
  • Proof sufficient to demonstrate impact without accessing real data.

Not allowed

  • Public scanning, denial of service, credential stuffing, persistence, phishing, malware, or destructive payloads.
  • Testing outside the written target and time window.
  • Publishing exploitable secrets or copied personal information.

Report template

Scope → methodology → finding title → affected component → evidence → impact → reproducible steps → remediation → retest result. Include a signed statement that the target was owned or explicitly authorised.

Game Development

Game Design and Playtest Pack

Prototype constraint: one core action, one clear goal, a 3–5 minute session, keyboard and touch controls, and original or properly licensed assets.

One-page GDD

  1. Player fantasy and audience.
  2. Core loop: action → feedback → consequence → next decision.
  3. Win, loss, restart, pause, and onboarding states.
  4. Input map for keyboard and touch.
  5. Scope cuts: what is deliberately excluded.

Playtest sheet

Record whether the player understood the goal, first successful action time, failure points, accessibility issues, delight/frustration moments, and one change to retest. Do not collect unnecessary personal data.

2D Animation

2D Production Planning Pack

Creative prompt: “A small character notices an unexpected light, hesitates, approaches it, and makes a choice.” Adapt the character and setting while keeping the story readable without dialogue.

Planning templates

  • Timing chart: frame range, key pose, spacing note, arc note, and intended weight.
  • Pose sheet: six thumbnails emphasizing silhouette and line of action.
  • Color script: four frames showing mood progression.
  • Feedback pass: issue, evidence, priority, revision, result.

For parallax, separate foreground, midground, background, atmosphere, and moving subject. Credit every non-original sound or texture.
